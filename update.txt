РОЛЬ

Ты — Senior Full-Stack Developer + Product Designer + UX Engineer.

Твоя задача — внести комплексные изменения в существующий проект DiyorAI, AI-помощника для путешествий по Узбекистану.

Не создавай новый проект с нуля. Сначала изучи существующую структуру проекта, текущие страницы, компоненты, навигацию, конструктор, готовые маршруты, гидов и логику расчёта бюджета.

Главный принцип:
Не ломать существующую функциональность, а аккуратно расширить её и улучшить UX.

После изменений весь интерфейс должен выглядеть как единый современный TravelTech-продукт.


1. КОНСТРУКТОР — КОЛИЧЕСТВО ПУТЕШЕСТВЕННИКОВ

Добавь в конструктор полноценную кастомизацию группы.

Поля:
- Количество взрослых
- Количество детей

Использовать понятные + / - контролы.

Пример:

Взрослые
[-] 2 [+]

Дети
[-] 0 [+]

Количество людей должно использоваться во всех последующих расчётах:
- стоимость отелей;
- билеты;
- трансфер;
- гид;
- общий бюджет;
- количество необходимых автомобилей;
- стоимость тура на человека;
- общая стоимость тура.

Если пользователь выбирает «Пара», автоматически:
Adults = 2
Children = 0

Если пользователь выбирает семью:
Adults = X
Children = Y

Количество человек должно передаваться во все следующие этапы построения маршрута.


2. ДАТЫ ПУТЕШЕСТВИЯ

В конструкторе добавить выбор конкретного периода:

С какой даты?
[ DD.MM.YYYY ]

По какую дату?
[ DD.MM.YYYY ]

После выбора автоматически рассчитывать общее количество дней.

Пример:
12 августа → 18 августа
7 дней

Установить разумный максимальный лимит длительности поездки, чтобы пользователь не мог создать некорректно длинный тур.

При превышении лимита показывать понятное сообщение.


3. АКТИВНЫЕ ДНИ И ДНИ ОТДЫХА

Сразу под блоком выбора дат разместить:

Продолжительность поездки: 7 дней

Активное путешествие
[-] 5 [+]

Дни отдыха
[-] 2 [+]

Правило:
Активные дни + Дни отдыха не должны превышать общее количество дней поездки.

Пример:
7 дней поездки
5 активных
2 отдыха

Если пользователь пытается поставить 6 активных и 3 дня отдыха, система должна показать ошибку и не позволять сохранить некорректное значение.


4. UX ДЛЯ +/- КНОПОК

Все поля, где пользователь меняет количество, должны визуально выглядеть как интерактивные элементы.

Использовать:
[-] 2 [+]

Кнопки должны иметь:
- hover state;
- active state;
- cursor;
- визуальное разделение;
- понятную интерактивность.

Это касается:
- взрослых;
- детей;
- активных дней;
- дней отдыха;
- других количественных параметров.

«Открыть конструктор»

7. ГОТОВЫЕ ТУРЫ

Создать/обновить отдельный блок:

Готовые туры

Каждый тур должен сразу показывать:
- направление;
- количество дней;
- формат;
- основные достопримечательности;
- количество человек, для которого рассчитан тур.

Отель, если входит:
- название;
- категория;
- количество ночей;
- стоимость.

Транспорт:
- самолёт;
- поезд;
- автомобиль;
- или «Транспорт не включён».

Примеры:
Ташкент → Самарканд
Поезд

Ташкент → Самарканд
Самолёт

Трансфер при необходимости:
- наличие;
- тип автомобиля;
- количество пассажиров;
- стоимость.

Показывать итоговую стоимость:
$XXX / человек

и при необходимости:
$XXX total.


8. БЮДЖЕТ ГОТОВОГО ТУРА

Готовые туры должны быть согласованы с бюджетом.

Если пользователь выбирает бюджет $500, тур стоимостью $850 нельзя показывать как полностью подходящий без явного предупреждения.

Показывать:

Ваш бюджет: $500
Стоимость тура: $460
Остаток: $40

или:

Стоимость тура: $620
⚠️ Превышает ваш бюджет на $120


9. КОНСТРУКТОР — ФОРМАТЫ И НАПРАВЛЕНИЯ

Расширить список направлений.

Минимально предусмотреть:
- Ташкент;
- Самарканд;
- Бухара;
- Хива;
- Шахрисабз;
- Ташкентская область;
- Чарвак;
- Чимган;
- Амирсой;
- другие релевантные туристические направления Узбекистана.

Не дублировать города.
Сделать направления удобными для выбора.


10. ТАШКЕНТСКАЯ ОБЛАСТЬ

Ташкентская область должна рассматриваться как полноценное направление.

Добавить low-budget варианты.

Чарвак:
- отдых у водохранилища;
- гастрономические точки;
- шашлык;
- однодневная поездка.

Чимган:
- горы;
- природа;
- прогулки;
- активный отдых.

Амирсой:
- горный курорт;
- лыжи / сезонные активности;
- канатные дороги;
- отдых.

Стоимость ориентировать на доступные low-budget сценарии, включая варианты примерно в диапазоне $30–40, если это соответствует данным проекта.

Не выдумывать реальные цены как гарантированные.
Если используются демоданные — явно воспринимать их как demo data.


11. ПОГОДНАЯ ПРОВЕРКА

Добавить проверку погодных условий, если weather API / данные уже подключены.

Если погода не подходит для выбранной активности:

🌧 В этот день ожидаются неподходящие погодные условия для горной активности.

Не просто показывать ошибку.

Предлагать альтернативу:
- музеи и исторические объекты;
- гастрономический маршрут;
- indoor activities;
- другой подходящий вариант.

Логика:
User plan → Weather check → Weather suitable?
YES → Keep activity
NO → Suggest alternatives

Пользователь должен иметь возможность:
- принять замену;
- оставить исходный вариант;
- пересобрать маршрут.

13. ЛОГИКА ТРАНСПОРТА И КОЛИЧЕСТВА ЛЮДЕЙ

Количество пассажиров должно учитываться.

Например:
7 человек

Если выбран трансфер, одной машины может быть недостаточно.

Предложить:
1 × Minivan

или:
2 × Sedan

в зависимости от вместимости.

Количество машин должно влиять на общую стоимость.


14. СТРОГИЙ КОНТРОЛЬ БЮДЖЕТА

DiyorAI должен строго контролировать бюджет на протяжении всего сценария.

Учитывать:

Hotel
+
Transport
+
Transfer
+
Guide
+
Activities
+

Total

Total Cost
vs

Если бюджет превышен, не показывать маленькое незаметное сообщение.

Показывать яркое предупреждение:

Ваш бюджет:
$700

Текущая стоимость:
$845

Превышение:
+$145

CTA:
«Пересчитать тур»

Дополнительно предложить:
- более дешёвый отель;
- другой транспорт;
- более дешёвый трансфер;
- low-budget activity;
- уменьшение количества платных активностей;
- альтернативный маршрут.

16. СОХРАНЕНИЕ СОСТОЯНИЯ

Информация конструктора должна сохраняться через cookies / local storage / другой подходящий механизм проекта.

После:
- перерасчёта;
- обновления страницы;
- перехода между страницами;

пользователь не должен терять заполненную форму.

Сохранять как минимум:
- Adults;
- Children;
- Start date;
- End date;
- Active days;
- Rest days;
- Budget;
- Interests;
- Destination;
- Departure city;
- Transport;
- Hotel;
- Transfer.

При повторном открытии конструктора восстанавливать состояние.

Не сохранять чувствительные персональные данные в cookies.


17. ИСПРАВИТЬ SCROLL ПОСЛЕ BUILD ROUTE

Сейчас при нажатии «Построить маршрут» страница скроллится вниз, из-за чего пользователь теряет контекст.

Исправить.

После построения маршрута пользователь должен оставаться в том же логическом положении.

Не делать неожиданного scroll-to-bottom.

Если результат отображается на этой же странице:
- раскрывать результат непосредственно рядом с формой;
- либо использовать отдельное состояние результата;
- либо показывать результат в заранее определённой области без резкого перемещения страницы.

Главный UX-принцип:
User should never lose context after clicking «Построить маршрут».

20. TRUST SCORE

Не показывать Trust Score как просто декоративное число.

При клике:
«Почему этот гид считается проверенным?»

Показывать:
✓ Личность подтверждена
✓ Квалификация подтверждена
✓ Опыт подтверждён
✓ Отзывы
✓ Специализация
✓ Языки

Если параметр отсутствует:
○ Не подтверждено

Не создавать ложное впечатление полной сертификации.


21. GUIDE MATCHING

Отдельно показывать:

Trust Score — надёжность гида.

Match Score — соответствие гида конкретному пользователю.

Например:

Trust Score
97/100

Match Score
94%

И обязательно:
«Почему этот гид подходит вам?»

Показывать:
✓ Совпадает специализация
✓ Работает в выбранном городе
✓ Подходит язык
✓ Подходит формат группы
✓ Доступен в выбранные даты

27. ПЕРСОНАЛИЗАЦИЯ

Все введённые пользователем параметры должны реально влиять на результат.

Нельзя создавать интерфейс, где пользователь вводит 7 человек, а результат рассчитывается как для 2.

Нельзя вводить $500 и получать маршрут стоимостью $900 без явного предупреждения.

Нельзя выбирать 5 активных дней и 2 дня отдыха и получать маршрут, который игнорирует эти параметры.

Каждый input должен быть связан с backend / calculation / recommendation logic или, если это demo data, с соответствующей mock-логикой.
