# Implementation Plan: Единый цифровой туристический помощник (MVP)

**Кейс:** TravelTech — Кейс B, Комитет по туризму
**Формат:** веб-приложение
**Ограничение:** без использования LLM API — заменяем rule-based / алгоритмическими решениями
**Данные:** только открытые источники (OSM, Wikidata/Wikipedia и т.п.)

---

## 1. Цель MVP

Собрать в одном веб-приложении три связанных модуля:

1. **Проверка информации** об объектах (вместо AI-гида — база фактов + поиск по достоверным источникам).
2. **Trip-planner** — генерация маршрута по интересам пользователя (вместо LLM — алгоритм подбора и построения маршрута).
3. **Поиск гида** — каталог гидов с фильтрацией и скорингом соответствия.

Цель MVP — показать работающий сквозной сценарий: пользователь выбирает интересы → получает маршрут → может проверить факт об объекте → может найти гида под этот маршрут.

## 2. Технологический стек

| Слой | Технология | Почему |
| --- | --- | --- |
| Frontend | **Next.js (React) + TypeScript + Tailwind CSS** | Быстрая разработка, SSR/SEO, один язык с бэком |
| Backend | **Next.js API routes / Node.js (Express, если нужен отдельный сервис)** | Минимум инфраструктуры для MVP |
| База данных | **PostgreSQL + PostGIS** | Нужны геозапросы (расстояния, кластеризация точек маршрута) |
| Полнотекстовый поиск | **PostgreSQL Full-Text Search** (или Meilisearch, если нужен более гибкий поиск фактов) | Поиск фактов об объектах без внешних платных сервисов |
| Карта | **MapLibre GL / Leaflet + OpenStreetMap tiles** | Бесплатно, открытые тайлы |
| Хостинг | **Vercel (frontend+API) + Supabase/Neon (Postgres) или Render** | Быстрый деплой, бесплатные тарифы для MVP |
| Геоданные | **OpenStreetMap (Overpass API), Wikidata, Wikipedia API** | Открытые, бесплатные, покрывают Узбекистан |

## 4. Модуль 1: Проверка информации (без LLM)

**Идея замены LLM:** не генерация ответа, а **поиск и сопоставление** введённого пользователем факта/вопроса с базой структурированных, проверенных фактов, привязанных к источнику.

### Как работает
1. При импорте данных каждый объект (памятник, музей, место паломничества) получает набор **фактов** (`object_facts`): текст факта, источник (Wikidata/Wikipedia/официальный сайт), дата сверки, уровень доверия источника (high/medium/low).
2. Пользователь выбирает объект (или вводит название / фразу гида) → приложение делает полнотекстовый поиск по `object_facts` (Postgres FTS / триграммное сходство `pg_trgm` для нечёткого совпадения — на случай, если гид сказал что-то похожее, но не дословно).
3. Результат: список релевантных проверенных фактов с указанием источника и датой, + пометка совпадает / не совпадает / нет данных для проверки.
4. Если факт не найден в базе — честный ответ «недостаточно данных для проверки» со ссылкой на официальный источник для самостоятельной проверки (не выдумываем ответ).

### Ключевые технические детали
- `pg_trgm` extension для fuzzy matching (устойчивость к перефразированию).
- Скоринг совпадения через `similarity()` — порог отсечения, например 0.3.
- Кэширование частых запросов (топ объектов) на уровне API.

### Что за скобками MVP
Полноценное понимание свободной речи гида (это была бы задача LLM/NLP) — в MVP заменяется на: (а) выбор объекта из списка/карты, (б) опционально — простой инпут с fuzzy-поиском по названию/ключевым словам.

## 5. Модуль 2: AI Trip-planner (без LLM) — алгоритмический подход

**Идея замены LLM:** генерация маршрута через **скоринг + оптимизацию маршрута**, а не текстовую генерацию.

### Шаг 1 — Сбор предпочтений пользователя
Простая форма (без свободного текста): категории интересов (история, архитектура, природа, паломничество, гастрономия и т.д.), количество дней, стартовый город/регион, темп поездки (спокойный/насыщенный), формат (одиночный путешественник да/нет).

### Шаг 2 — Отбор объектов (Scoring)
Для каждого объекта в регионе считаем score:

```
score(object) = w1 * match(tags_interest, object.category)
              + w2 * popularity_or_rating
              + w3 * (1 / distance_from_base_point)
```

Отбираем top-N объектов по score с учётом ограничения "не более K объектов в день" (исходя из среднего времени на посещение).

### Шаг 3 — Построение маршрута (Routing)
1. Кластеризация отобранных объектов по дням (например, k-means по координатам с ограничением по числу точек в кластере = дни поездки).
2. Внутри каждого дня — упорядочивание точек эвристикой ближайшего соседа (nearest neighbor) с последующей локальной оптимизацией (2-opt) для минимизации общего пробега.
3. Расчёт расстояний/времени в пути через OSRM (открытый self-hosted роутер) или прямые линии + средняя скорость, если OSRM не поднимаем в рамках MVP.

### Шаг 4 — Отдельный сценарий одиночного путешественника
Флаг `solo_traveler=true` добавляет в scoring объектов дополнительный вес местам с хорошей транспортной доступностью и общественной освещённостью/посещаемостью (безопасность), и в выдаче маршрута — рекомендацию сопровождающего гида в вечернее время/для удалённых локаций.

### Что за скобками MVP
Динамическая корректировка маршрута "на лету" в диалоге — в MVP заменяется на кнопку "пересчитать" с изменёнными параметрами формы.

## 6. Модуль 3: Поиск гида

### Как работает (без LLM)
1. Каталог гидов (`guides`): регион работы, языки, специализация (теги, пересекающиеся с категориями интересов объектов), рейтинг (demo-данные на MVP), цена.
2. После построения маршрута система считает **score соответствия** гида маршруту:

```
guide_score = overlap(guide.specialization_tags, trip.object_categories)
            + match(guide.region, trip.region)
            + language_match(guide.languages, user.language)
```

3. Топ-3–5 гидов показываются как рекомендация к сформированному маршруту + доступен независимый поиск с фильтрами (регион, язык, специализация, цена).

### Данные о гидах на MVP
Реальной базы от партнёра нет → используем **структурированные demo-данные** (явно помечены в интерфейсе как демо / "предпросмотр — в проде данные от Комитета по туризму"), чтобы не выдавать вымышленные данные за реальные.

## 7. Модель данных (упрощённо)

```sql
objects (
  id, name, category, lat, lon, region, description_short,
  source_url, popularity_score
)

object_facts (
  id, object_id FK, fact_text, source_name, source_url,
  trust_level ENUM('high','medium','low'), verified_at
)

guides (
  id, name, region, languages TEXT[], specialization_tags TEXT[],
  rating, price_range, is_demo_data BOOLEAN
)

trips (
  id, session_id, interests TEXT[], days INT,
  solo_traveler BOOLEAN, region, created_at
)

trip_days (
  id, trip_id FK, day_number, ordered_object_ids INT[]
)
```

## 9. Этапы разработки (спринт под быстрый запуск)

### Фаза 0 — Подготовка (день 0)
- Настройка репозитория, CI, деплой-пайплайна (Vercel + БД).
- Схема БД, миграции.

### Фаза 1 — Данные (параллельно с фронтом)
- Скрипты импорта из OSM (объекты + координаты + категории) для 3–5 ключевых регионов (Самарканд, Бухара, Хива, Ташкент — можно сузить дальше).
- Импорт фактов из Wikidata/Wikipedia, привязка к объектам.
- Seed demo-данных по гидам.

### Фаза 2 — Backend / API
- `/api/objects` — выдача объектов с фильтрами.
- `/api/verify` — fact-matching endpoint.
- `/api/plan-trip` — scoring + routing логика.
- `/api/guides` — поиск и скоринг гидов.

### Фаза 3 — Frontend
- Онбординг (форма интересов/дней/региона).
- Экран маршрута: карта + список по дням.
- Экран проверки факта (выбор объекта → факты + источники).
- Каталог и карточки гидов.

### Фаза 4 — Интеграция и сквозной сценарий
- Связка: маршрут → рекомендованные гиды → проверка факта об объекте из маршрута.
- Обработка edge cases: пустая выдача, объект без фактов, регион без гидов.

### Фаза 5 — Полировка и демо
- UI-доводка, адаптивность (мобильный сценарий для "во время путешествия").
- Подготовка демо-сценария и презентации.

*Фазы можно вести частично параллельно (данные + бэкенд + фронт одновременно), если в команде более 1–2 разработчиков.*

## 10. Что входит в MVP / что нет

**Входит:**
- Работающий алгоритмический trip-planner (без LLM).
- Проверка фактов по базе с указанием источника и уровня доверия.
- Каталог и скоринг гидов (на demo-данных).
- Единый сквозной пользовательский путь на вебе.

**Не входит (roadmap после MVP):**
- Интеграция LLM API для естественного диалога и более гибкой проверки утверждений гида.
- Реальная база гидов от Комитета по туризму (сейчас — demo-данные).
- Мобильное приложение (только адаптивный веб).
- Онлайн-бронирование гида / платежи.
- Многоязычность интерфейса (на MVP — один язык, архитектура должна закладывать i18n).

---

## 11. Риски и ограничения

- **Качество/полнота OSM-данных** по конкретным регионам Узбекистана может быть неравномерной — нужна ручная валидация топ-объектов перед демо.
- **Demo-данные гидов** нельзя выдавать за реальные пользователю без пометки — юридический и репутационный риск.
- **Fuzzy-поиск фактов** без LLM ограничен по гибкости — не поймёт сильно перефразированный вопрос; на MVP это компенсируется выбором объекта из списка вместо свободного текста.
- **Роутинг без OSRM** (прямые линии) даёт менее точное время в пути — приемлемо для MVP, отметить как техдолг.

---

## 12. Дальнейшее развитие (после MVP)

1. Подключение LLM API для естественного языка (диалог, разбор утверждений гида "как есть", более умная генерация описания маршрута).
2. Подключение реальных данных Комитета по туризму (факты, база гидов, API).
3. Self-hosted OSRM для точного расчёта времени в пути.
4. Личный кабинет, сохранение маршрутов, отзывы о гидах.
5. Многоязычность (RU/UZ/EN) и мобильное приложение.
